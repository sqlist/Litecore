# LiteCore 后续路线图（ROADMAP）

> 本文回答三个问题：中期答辩之后，我们做什么？怎么做？做完之后，能拿出什么给评委和实验室导师看？
> 本文是后续工作的执行手册，也是结题材料、论文素材的来源清单。

**v2 修订说明**（根据外部评审修订）：

- 验收单位从"一条曲线"改为"一个证据包"（九件套，见第三节）；曲线是展示形式，不是完成本身。
- 修正了三处技术错误：信道模型接口不能原样复用（缺时间/位置/速度语义）、"切换成功率"在只做决策不做切换时无法定义、业务类别应绑会话而不是绑注册。
- 重排时间线：先修"实验底座"，A 首版只做单一隧道轨迹，B1 先离线验证再加 RPC，B2 移出本轮交付。

## 一、一句话总览

把 LiteCore 从"教学演示平台"升级成"轨道通信实验平台"。六个阶段，按依赖顺序走，**每个阶段产出一个证据包**。

| 顺序 | 阶段 | 一句话 | 证据包的核心产出 |
| --- | --- | --- | --- |
| 0 | 实验底座 | 先把"实验"两个字立起来 | 可复现的实验规程与配套脚本 |
| 1a | A0 单一隧道轨迹 | 让信道"像列车一样动起来" | 一条隧道轨迹的导入、验证与回放 |
| 1b | A1+B1 邻区轨迹与离线决策 | 看着信号变化提前做切换 | 决策算法 vs 阈值法基线的对比 |
| 2 | D 故障注入 | 把演示容错变成自动测量 | 故障下的可靠性测量报告 |
| 3 | C QoS 分级（可选） | 列控信令优先于乘客娱乐 | 拥塞下时延满足率对比 |
| 4 | B2 先建后断（独立课题） | 会话路径不断流迁移 | 架构论证 + 最小数据面 |

时间预估：Phase 0 约 1 周；A0 约 2~3 周；A1+B1 约 4 周；D 约 2 周；C 约 2~4 周；B2 是课题级工作量，单独排期。主线（0 → A0 → A1+B1）累计约 7~8 周。**D 只依赖 Phase 0**，人手够时可以和 A0 并行。

> 前提：以下所有阶段都安排在**中期答辩之后**开工。答辩前代码保持冻结，不碰 amf/、smf/、upf/、ue/、proto/。

## 二、我们现在的起点（一段话讲清楚）

今天 LiteCore 有三件事还停在"演示"层面，而且各有各的硬限制：

- **信道是"抽签"**：每次注册从四种固定场景里抽一个值（[ue/channel.go](../ue/channel.go)）。而且 benchmark 是"一个 UE 抽一次、立刻注册"（[ue/benchmark.go:39-52](../ue/benchmark.go#L39-L52)）——就算做出了时间序列，现在的消费方式也用不上。
- **转发是"计数"**：UPF 每秒给每个会话加 10 个包（[upf/handler.go:75-93](../upf/handler.go#L75-L93)），没有队列、没有时延概念。
- **容错是"手动演示"**：答辩时当着评委的面停掉 SMF 再恢复。而且三个网元都是内存状态，单服务重启会留下状态失配——[ARCHITECTURE.md](../docs/ARCHITECTURE.md) 的"已知限制"里我们自己写明了这一点。

路线图要做的，就是在这三个真实起点上，把"演示"一个个变成"实验"。

## 三、验收单位：证据包（九件套）

每个阶段做完，交付的不是一张图，而是一个证据包。九件套如下，缺一不可：

1. **研究问题**：这个阶段要回答的问题是什么？（一句话）
2. **模型来源**：用的信道/故障/QoS 模型来自哪里？标准、文献还是导师数据？
3. **基线**：拿什么做对比？（改进前 vs 改进后；新算法 vs 阈值法）
4. **配置与 seeds**：机器配置、IP 池大小、阈值参数、固定 seed、run-id——保证任何人能复现。
5. **原始数据**：CSV/轨迹文件原样归档，不做任何事后加工。
6. **统计区间**：每组实验至少三次，报告均值和波动范围。
7. **绘图脚本**：从原始数据到图表的脚本入仓库，图必须能从数据重新生成。
8. **结论**：数据说明了什么。
9. **局限**：数据不能说明什么——模拟不是实测、测量不是保证。

## 四、Phase 0：实验底座（约 1 周，最先做）

**通俗版**：正式做实验之前，先把"实验"两个字立起来——让每一次实验跑完，数据、配置、图表都能互相印证，谁都能复现。

**做什么**（控制在 1 周内的轻量规模，不搞成新项目）：

- **统一时间戳**：日志和 CSV 的每一条记录都带同一时钟域的时间戳（如"实验开始后第 N 毫秒"）。
- **配置快照**：每次实验自动写一份 `run_config.json`（机器配置、Go 版本、IP 池大小、阈值参数、seed），和结果放在一起。
- **配对 seed**：基线和实验组共用同一批信道样本，只改要比较的那一个变量。
- **原始数据归档**：现有 CSV 输出已经不错，补一条规矩——原始文件只读归档。
- **绘图脚本**：一个把 CSV 转成标准图表的脚本（放 `scripts/` 下），保证论文里的每张图都能重新生成。
- **端到端冒烟测试**：一个脚本，实验前先起栈、注册一台、注销、检查通过——保证"测量日"不浪费在环境问题上。
- **状态一致性检查**：一个脚本，实验后核对 AMF 的 UE 记录、SMF 的会话、UPF 的规则是否互相一致。这是方向 D 的关键工具，先在这里做好。

**验收**：跑一次完整实验，九件套齐全，换一台机器按规程能复现。

## 五、Phase 1a · 方向 A0：单一隧道轨迹（约 2~3 周）

**通俗版**：现在的信道是"抽签"。真实的列车在跑，信号是连续变化的——进隧道掉下去，出隧道慢慢回来。我们要做的第一版只有一件事：一条隧道场景的信道轨迹，能导入、能验证、能原样回放。

**做什么**：

1. **先设计 `RadioTrace`（可回放的轨迹）**。现有 `ChannelModel.Sample(rng)` 没有时间、位置、速度语义，不能靠换实现来凑。轨迹至少包含：时间 t、位置 x、速度 v、服务小区信号功率与 SINR、邻区信号功率与 SINR。存成 CSV/JSON 文件，导入后可确定性地逐点回放。
2. **确认模型来源**。找导师确认轨道信道模型/数据的输出形式——是公式？数据文件？还是指定文献？
   - 拿到了 → 按它的形式生成轨迹；
   - 拿不到 → 用 3GPP 文献模型（TR 38.901）自己搭：**完整轨迹 = 路径损耗（场景几何）+ 阴影（相关对数正态）+ 小尺度（Jakes 多普勒谱）三部分组合**。注意：Jakes 谱只是小尺度衰落的多普勒部分，单靠它推不出隧道、站台、路堑的完整信号轨迹。
3. **首版范围只做一条隧道轨迹**（进隧道跌落—出隧道恢复）。不承诺四种地形、不承诺完整标准模型——先跑通"导入→验证→回放"整条链路。
4. **改造 benchmark 的消费方式**：长跑回放整条轨迹，CSV 里多出轨迹时间列（现有"一 UE 一采样"的方式要跟着改）。

**数字口径**：多普勒频移，350 km/h @ 3.5 GHz 约 1.13 kHz，@ 2.1 GHz 约 681 Hz。报告里写"国内 5G-R 试验频段"并给出具体出处（如工信部试验说明、测试线研究文献），**引用前自行核对链接**，不要泛称"频段规划"。

**验收**：证据包（九件套），其中模型来源说明要写明"哪份标准/文献、哪组参数、为什么可信"；图是"列车过隧道：信号跌落—恢复"轨迹。

**坑**：导师模型拿不到时，**明说用了标准模型**，别含糊说"导师的"——评委追问一次就会穿帮。

## 六、Phase 1b · 方向 A1+B1：邻区轨迹与离线决策实验（约 4 周）

**通俗版**：列车一直在跑，信号一直在变。这一阶段回答一个问题：**能不能看着信号下滑、提前判断"该切换了"**——并且只看判断准不准，不真的执行切换。

**做什么**：

1. **A1：轨迹加邻区**。把 A0 的轨迹扩展出邻区小区信号（服务小区变差的同时邻区变好），切换决策才有素材。
2. **B1：先离线、后上线**。先用轨迹文件**离线**跑决策算法——输入是滑窗内的信道片段，输出是切换触发点。算法调好之前不写一行 RPC，避免同时调试算法和分布式系统。
3. **对比基线**：阈值法（信号低于门限且邻区高于门限，加迟滞）。B1 的决策算法必须和它比。
4. **指标**（离线可测，定义清晰）：**提前量**（决策点比"信号交叉点"早多久）、**漏触发率**（该触发没触发）、**误触发率**（不该触发却触发）、**乒乓率**（短时间内反复来回切换）、**决策延迟**。
5. 离线验证通过后，再加周期上报 RPC 做在线实验。

**诚实口径**：B1 验证的是"移动性**决策**"，不执行切换、不迁移会话——所以没有"切换成功率"这种指标（不执行切换时它无法定义）。报告里写"移动性决策仿真"。

**验收**：证据包——决策算法 vs 阈值法基线的五指标对比；如果决策算法赢了，这就是论文"移动性管理"一节的素材。

## 七、Phase 2 · 方向 D：故障注入与可靠性测量（约 2 周，可与 A0 并行）

**通俗版**：答辩时"停掉 SMF 再恢复"是手动演示。现在把它自动化：定时杀掉服务、同时持续注册、自动统计成功率——把"能容错"从口头证明变成数字证明。

**做什么**：

1. **定范围**：单平台（Docker 或 K8s 二选一）、单故障（只注入 SMF 崩溃）、固定负载。跑通了再加别的。
2. **先定义故障模型**（方法论部分）：例如"每 60 秒杀一次 SMF，重启耗时约 10 秒，实验持续 30 分钟"。
3. **写编排脚本**（放 `scripts/` 下）：定时 kill/重启容器或 Pod，同时驱动 benchmark 持续注册。
4. **指标拆分**（这一条是重点）：
   - **首次尝试成功率**：不靠重试能成多少；
   - **重试后成功率**：加上重试机制后能成多少——两个数字的差就是你们重试机制的价值；
   - **MTTR**：从故障到服务恢复可用的时间；
   - **孤儿资源**：实验后残留的会话/规则/IP 占用数；
   - **状态一致性**：跑 Phase 0 的一致性检查，报告失配情况——内存状态的局限必须出现在证据包里。

**诚实口径**：这叫"**故障下的可靠性测量**"，不叫容错证明、更不叫高可用。正确表述是"在定义的故障模型下（故障间隔 X、恢复时间 Y），测得首试成功率/重试后成功率/MTTR 为……"。数字随 kill 频率变化是可调的，**不宣称"我们达到了 99.9%"**。

**验收**：证据包——两条成功率曲线（首试 vs 重试后）、MTTR、一致性检查结果与局限说明。

## 八、Phase 3 · 方向 C：QoS 分级实验（可选，人力不足就砍）

**通俗版**：列车上同时有两类业务：列控信令（出事就危险，必须快）和乘客刷视频（慢半秒无所谓）。拥塞时系统必须让信令插队。这个实验回答：拥塞时，高优先级业务的时延能不能守住。

**做什么**：

1. **业务类别绑会话，不绑注册**。业务类别随 `CreateSession`/`CreateRule` 一路传下去——`DNN` 字段已经在 [upf/handler.go](../upf/handler.go) 的转发规则里，顺势扩展。
2. **先查标准**：各类业务的时延指标（信令级几十毫秒、娱乐级几百毫秒）——数字有标准出处之前不进报告。
3. **UPF 从"计数器"升级成"排队模型"，模型参数逐项定义清楚**（这是本阶段最大的工作量，原估时偏乐观的原因）：
   - 到达过程：包怎么来（间隔分布）；
   - 包大小：多少字节；
   - 服务能力：UPF 每单位时间能处理多少；
   - 缓存大小：排多长的队；
   - 基线调度：FIFO；
   - 实验调度：按优先级（严格优先或加权）；
   - 饥饿上限：低优先级最多等多久（防止"低优先级永远出不了队"这种假结论）。
4. **拥塞实验**：逐步加负载，对比高/低优先级业务的时延满足率。

**验收**：证据包——"拥塞程度 vs 高/低优先级时延满足率"对比曲线。

**两个坑**：

- 这个实验叫"QoS 分级"，**不叫"切片"**。真切片要 NSSAI 和切片间隔离，我们没有；评委一句"NSSAI 怎么设计的"就答不上来。
- 总工期不足 8~10 周时，**直接砍掉 C**——它是加分项，不是主线。

## 九、Phase 4 · 方向 B2：先建后断（独立课题，本轮不承诺交付）

**通俗版**：B1 只做判断，B2 才做真正的"切换执行"——切换瞬间通信不中断。这是四个方向里最重的一个，**单独立项**，不在本轮路线图的交付承诺里。

**做什么**（本轮只做两件事）：

1. **架构论证**：按标准 5G 的语义建模。切换不是"建两个 PDU 会话"（我们 SMF 目前是 byUE 一对一，但硬凑成两个会话不符合 3GPP 语义）；标准流程（TS 23.502）的核心是**既有 PDU 会话的路径更新**——会话上下文更新 + 目标 N3 路径建立。对应到我们的代码，先引入 `AccessPath`/`ForwardingPath`（会话内的转发路径）概念，切换 = 路径更新，再决定是否需要多会话。
2. **最小数据面**：要测"中断时长"，必须先有探测包。当前 UPF 只是计数器，**没有真实或模拟的数据包可测中断**。最小数据面 = UPF 周期发送模拟探测包并记录到达时间，先让"中断时长"成为可测量。

**坑**：B2 要动 SMF 的会话状态机、幂等判定、补偿回滚、IP 池——全是项目最值钱、`-race` 测试护着的那层。顺序上放最后是刻意的：等 Phase 0 的底座、A0/A1 的轨迹、B1 的决策算法、D 的测量方法全部就位之后再动它。

## 十、四条诚实红线（所有证据包通用）

1. **模拟信道不叫实测**：模型来源必须写明，是标准/文献模型就是标准/文献模型。
2. **QoS 分级不叫切片**：没有 NSSAI 和切片隔离，就不能用这个词。
3. **故障测量不叫高可用**：可用性数字是"特定故障模型下的测量值"，不是系统保证。
4. **决策仿真不叫切换执行**：B1 只做判断，没有切换成功率；切换执行是 B2 的事。

## 十一、需要实验室和导师提供的三样东西

1. **真实信道模型或实测数据**——A0 的关键输入，也是"和轨道有什么关系"的最硬答案。
2. **标准核实渠道**——A1/B1 的切换间隔、C 的时延指标、频段口径等数字，必须有标准出处。
3. **（远期）对标机会**——如果实验室愿意，用 LiteCore 与 OAI/Open5GS 在部署时间、镜像体积、读懂逻辑的时间、修改→验证周期四个维度做量化对比。这是大创立项时的对比点，放在 Phase 0 的实验框架里顺手就能做。
